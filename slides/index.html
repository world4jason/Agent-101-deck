Agent 教學，
其實是軟工流程教學

從需求、Issue、PR 到 Release 後 QA：先學流程，再把可驗收任務交給 Agent。

主軸只有一件事：一張工作卡，如何安全走完整條線。
課程定位

不要先問「Agent 怎麼變強」；
先問流程怎麼不失控

常見誤解

「你幫我把網站做好。」結果 scope creep、fake done、自己做自己審。

課程做法

把工作拆成 issue：有 AC、有 scope、有 evidence、有人 review。

核心句

Agent 不取代流程；Agent 需要流程。流程越清楚，越能委派。

課程地圖

4 個問題，串成一條完整工作流

01一個需求，怎麼變成軟體？先建立流程地圖與角色語言。

04哪些工作可以交給 Agent？同一條流程，角色換成 Agent。
需求 → Issue + AC → WIP=1 → Branch → PR → Verify → Review → Merge → Release → Post-release QA → Done
01
人類軟體開發流程

一個需求，
怎麼變成軟體？

先不要談 Agent。先看懂需求、工作卡、PR、QA 在整條線上的位置。

生活譬喻

把軟體專案想成「辦一場讀書會」

1｜需求

想辦讀書會，但時間、人數、場地還不清楚。

2｜工作卡

訂場地、做報名表、寄通知、確認名單。

3｜證據

訂位截圖、報名名單、通知寄送紀錄。

4｜交付後確認

活動當天確認場地可用、名單正確、通知沒漏。

工作卡 = Issue｜完成條件 = AC｜證據 = Evidence｜上線後確認 = Post-release QA
流程全貌

一個需求到上線，會走同一條線

→

→

→
Verify測試證據
→

→

Done關卡
先問清楚 → 再做小步 → 最後看證據。
角色地圖

同一個需求，會被不同角色用不同角度看

PO

定義為什麼做｜價值與驗收標準

PM / Scrum

控流程與節奏｜排優先、移阻礙

Dev

實作變更｜code / 文件 / migration

QA

驗證行為｜測試、截圖、找 bug

Reviewer

守品質｜審 diff、架構、風險

Ops

管上線｜部署、監控、回滾

小白詞彙表

Ticket、Issue、PR、Release 到底是什麼？

Ticket一張工作申請單。
Issue一張可追蹤工作卡。
PR「請大家看我的變更。」
Release把核准變更交到使用者手上。
Post-release QA上線後再確認一次。
很多公司會混用 Ticket / Issue；這堂課先統一：Issue = 要被推進的一張工作卡。
02
工作拆解

怎麼把需求寫成
可以開工的工作？

不要先背 Epic / Story / Task。先會把模糊需求變成一張有邊界、可驗收的 Issue。

Lead by example

從一個模糊需求開始：活動報名頁

RUNNING EXAMPLE · 活動報名頁
「我們下個月要辦讀書會，想要一個報名頁，大家可以填資料，也能收到確認訊息。」
使用者主辦人、參加者
價值少用訊息來回確認
風險漏填、重複報名、通知失敗
限制先支援手機，不做付款
拆解原則

大到一張卡講不清楚，再往上分組

Project / Epic

大目標分組。用來追蹤一包工作；不是每次都需要。

Issue

真正開工單位。一張 issue 對一個 branch / PR / evidence。

Checklist

Issue 內的小步。太小不值得獨立驗收，就不要拆出去。

Story

選修寫法。需要講 user value 時再用。

大需求用 Project 分組；真正開工看 Issue；Issue 太小就變 Checklist；Story 可用但不是必經關卡。

Issue #12

手機版報名表單

本堂課主角：可獨立 PR、可驗收
Issue #13

主辦人名單頁

另一張工作卡，不跟 #12 混做

Story optional

Story 不是階級，是一種寫需求的方法

User Story 寫法

作為參加者，我想用手機完成讀書會報名，讓我不用私訊主辦人來回確認。

Plain Issue 寫法

修正手機版報名表單：390px 寬度下可填資料、送出，並顯示成功或重複 email 提醒。

需要說明「誰得到什麼價值」→ Story。Bug / UI / 文案 / infra / CI → 直接 Issue。
Issue template

一張好 Issue，比一段聰明 prompt 更重要

Problem哪裡不對？誰受影響？
Goal完成後改善什麼？
Scope這次做 / 不做哪些事？
Acceptance Criteria怎樣算完成，最好可測。
Context相關檔案、設計、前置決策。
Constraints風格、效能、相容性、風險。
Evidence截圖、測試、log、PR diff。
Stop rule遇到什麼要停下來問人？
沒有 AC，不開工；沒有 Evidence，不算 Done。

Issue #12：手機版報名表單送出與驗證

#12 · 手機版報名表單送出與驗證
問題 / 目標

手機報名不順；390px 可完成送出。

非目標

Acceptance Criteria

2. 姓名 / email 必填

03
Git / PR / Release

一張 Issue，
怎麼安全走到上線？

Git / PR / QA / Review 不是儀式，而是把修改隔離、檢查、驗證，再送到真實使用者手上。

Kanban / WIP

一張 Issue 從左走到右；初學先 WIP = 1

Backlog

AC 已清楚

Issue #12
WIP = 1

Verify

下一站

Review

獨立審查

Done

最後關卡
先把一張卡完整走完，再開下一張卡。卡在 Build，就不要再拿新的。
Git basics

Git 只先懂 4 個字：Repo、Branch、Commit、Push

Repo

共同資料夾。專案主要倉庫。

Branch

草稿分身。為 #12 開分支。

Commit

存檔點。記錄一次有意義修改。

Push

上傳草稿。PR 才看得到更新。

最小 Git 流程：開 branch → 修改 → commit → push → 開 PR。

Reviewer 結論

Request Changes

Dev 修正後繼續 push 到同一 branch，PR 自動更新，不用重開。

Code Review

Comment、Approve、Request Changes：意思完全不同

Comment

留下意見或提問，不一定阻擋合併。

Approve

符合 AC、證據足夠，可以進入 merge / release。

Request Changes

有 bug、缺 evidence、scope creep 或風險，需修完再看。

關卡分離

QA、Review、Merge、Release 是不同關卡

Verify / QA

對照 AC 跑測試，產出截圖、log、測試結果。

Review

看 diff 與設計風險，找 scope creep、缺測試、缺證據。

Merge

把核准的分支併回主線。

Release

把主線變更交給使用者。

Done 不是自己說了算。缺一關，就只是「接近完成」。
Post-release QA

Release 後不是結束：要確認真的在真實環境可用

Smoke test

手機打開、填表、送出、看到成功訊息。

Monitoring

看錯誤、速度、流量、通知是否異常。

Feedback

收第一批問題，決定熱修或排下一張 issue。

Rollback plan

嚴重失敗時知道如何回上一版。

Post-release QA 不是 retro。它是上線後確認功能真的能用。
04
Agent 接手

哪些工作，
可以交給 Agent？

現在才談 Agent：不是換一套魔法，而是把剛才的人類工作流交給不同 Agent 產出工件與證據。

Agent 流派的本質

BMAD / LongHorizon 這類方法，本質都在補「流程缺口」

Task state 外化

任務狀態、AC、證據不要只存在聊天裡。

Bounded execution

每次只做有邊界的一小段，避免 scope creep。

Independent audit

做事與檢查分開，避免 one-agent bias。

Goal re-anchoring

每輪回到原始目標與 AC，避免越做越偏。

不用先背框架名詞。先看它們到底在解哪一個軟工問題。
角色轉 Agent

Agent 能取代的是「可驗收任務」，不是責任本身

Agent 角色適合承接仍需人類負責
PO Agent整理 issue、AC、非目標、風險價值判斷與優先順序
PM / Scrum Agent整理看板、找卡住、提醒缺證據排程承諾與取捨
Dev Agent依 issue 實作、重構、補文件高風險架構決策
QA Agent產生測試、跑 smoke、收 evidence接受風險
Review Agent對照 AC 審 diff、找 scope creep最終合併與發布授權

Workshop

同一個需求，分三輪交給 Agent

Round 1｜PO Agent

輸入：模糊需求

輸出：是否需要 Project / Issue / AC / 非目標

Round 2｜Dev Agent

輸入：Ready issue

輸出：修改計畫 / diff / PR 摘要

Round 3｜QA + Review Agent

輸入：PR / AC / evidence

輸出：測試結果 / review 結論 / release checklist

講師反覆問：這張卡在哪一欄？完成定義是什麼？證據在哪裡？誰有權核准下一步？
常見失控模式

Agent 失控通常不是模型爛，是流程缺洞

Scope creep

越做越多 → 把非目標寫進 issue；每輪只改一種問題。

Context swamp

上下文太多 → 改用 issue state / notes 摘要。

Fake done

沒證據就說完成 → Done 需要測試、截圖、diff、review 結論。

One-agent bias

自己做自己審 → Dev 與 QA / Review 分開。
