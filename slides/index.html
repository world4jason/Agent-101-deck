S0-01Core課程定位

Agent 參與軟體工程，
不會取代流程與責任

先看產品工作怎麼流動，再看哪些有邊界、可驗收的工作能交給 Agent。

不要求學員手寫程式；也不承諾一堂課就能讓人變成後端工程師，或保證產品成功。
主線：需求、角色、工作卡、驗收與證據先到位，Agent 才能安全承接工作。

S1-02Core人類責任視角

角色是責任視角，不是固定職稱

同一需求：A 喜歡 B、B 也喜歡 A 才成立配對。先問「這是誰要回答的問題？」

責任視角在 Matching 需求中負責什麼要回答的問題
PO判斷價值、目標與接受條件要解決誰的問題？怎樣算符合需求？
Frontend操作流程與介面呈現如何按喜歡，並看見配對結果？
Backend身分、資料、API 與配對規則怎樣確認雙方選擇並保存結果？
QA核對行為與失敗路徑單向喜歡、沒按喜歡時會怎樣？
Reviewer檢查變更、範圍與風險差異是否符合約定？有沒有漏掉風險？
Ops發布、環境、運行與恢復上線的是哪一版？出問題如何恢復？
PO、PM 與 Scrum Master 的責任不同；一人可承擔多個視角，不必有同名職位。
S1-03Core工作拆解與驗收

工作分組用 Epic，能驗收的工作寫成 Issue

本課兩層 Matching Epic

讓 A、B、C 使用者依雙向喜歡規則完成配對。

Issue：雙向喜歡才建立配對Goal：讓使用者找到互相選擇的對象。AC 情境：A 喜歡 B、B 尚未回應時不配對；B 也喜歡 A 才配對；C 單向喜歡 B 時也不配對。
GitHub Project ≠ Epic

Project 是整理與追蹤工件的地方；Epic 是本課用來分組的大工作。

本課只用 Epic → Issue。Goal 用一句話交代為誰、為什麼；AC 寫可觀察情境。

Kanban 本身不規定工作項目要長什麼樣子；User Story 起源於 XP，Scrum 與 Kanban 都不要求一定寫成 User Story。

User Story 詞條留在 Appendix A1；主線不再加入其他工作項目層級。

S1-04Core工作節奏

Sprint 與 Kanban 是不同的工作節奏

Sprint

固定週期

  • 按週期規劃一批工作。
  • 在週期節點檢視結果與回饋。
  • 本課只作方法對照，不教 Scrum 儀式。
本課採用

Kanban 持續流動

  • 依容量拉取下一張 Ready 卡。
  • 工作持續流動，不等固定週期才交付。
  • 新回饋可觸發排序調整。
課程採 Kanban；Sprint 只用來看出節奏與回饋方式的差別。
S2-01Core委派邊界

把模糊需求整理成有邊界的工作卡

先和 Agent 釐清需求，再由人決定範圍；沒有核准的額外功能，執行者不能自行加入。

Matching Issue｜雙向喜歡才建立配對
Goal

讓使用者只看見雙方都選擇的配對。

AC｜可觀察情境

A 喜歡 B、B 尚未喜歡 A：不成立配對。B 也喜歡 A：建立配對。

Out-of-scope

本卡不做聊天室、推薦演算法或付款。

Stop rule

需要新資料、改變授權或遇到無法排除的阻礙時，先停下問 PO。

可採用的教學約定

一張可驗收卡配一個小 PR，方便看差異與證據；這不是 GitHub 限制。

S2-02CoreAC 與 DoD

「做對了嗎？」看 AC；「收尾了嗎？」看 DoD

AC｜Acceptance Criteria這張卡的行為是否符合約定？

PO 與團隊為單卡約定；各卡情境不同。

DoD｜Definition of Done共通收尾條件是否全部完成？

全課共用；每條都須有可核對證據。

1PR 審查通過，阻擋項已處理。
2上線後基本操作檢查通過，附版本與操作證據。
3變更未超出已核准範圍。
4受影響的既有功能檢查通過，附證據。

PO 接受前確認 DoD 1、3、4；授權上線後補第 2 條。基本操作通過不代表 AC 全過。

AC 過、DoD 未過

Agent 環境可配對；PR 未審、未上線。

DoD 過、AC 未過

已審查、上線；B 未 Like 就成立配對。

超出核准範圍

順手加聊天室：Request Changes；多做部分交 PO 決定是否另開卡。

Done = AC 獲 PO 接受 ＋ DoD 四條全過。 Agent 易順手多做；需求是否符合、範圍是否越界須由 PO／團隊核對，不能只靠自動檢查。
S2-03Core驗收與發布

驗收、核准、發布與上線後檢查各有關卡

  1. AC 約定先說清楚行為與範圍。
  2. 實作依核准內容修改。
  3. QA核對行為與失敗路徑；CI 只是其中一種證據。
  4. Review檢查 diff、scope 與風險。
  5. PO 接受在能對應候選版本的驗收環境依 AC 接受；確認 DoD 1、3、4。
  6. 授權發布Review 核准本身不授權 merge 或上線。
  7. 上線後檢查補 DoD 2 的基本操作證據。
  8. DoneAC 接受且 DoD 全過。
Comment

提出意見或問題。

Approve

Review 的審查結論。

Request Changes

要求修正；QA／Review 可依 AC 或 DoD 退回。

Merge、Issue 關閉、部署、對使用者開放與 GitHub Release 不是同一件事，也不能單獨代表交付完成。
S2-04Core證據與版本

證據只證明它實際覆蓋的行為與版本

逐條 AC 留下可核對紀錄

怎麼驗實際操作或檢查方法。
預期／實際逐項記錄並對照結果。
狀態PASSFAILNOT RUNBLOCKED
版本／環境標明版號與驗收環境；受阻須寫原因。
來源附連結、截圖或測試結果供核對。

一起判斷

這份證據證明什麼？不能證明什麼？還缺什麼？

測試沒跑卻報成功應標 NOT RUN。
驗收環境還是舊版不能證明候選版通過。
測試被刪除／跳過／弱化Review 核對測試差異。
驗收網址不等於版本證據；學員核對 Agent 提供的版本／環境是否對應候選版。高風險資料、授權、付費或不可逆變更，須由具能力者技術審查；技術審查與風險接受分開決定。
S2-05Core版本狀態

用共享檔案的比喻核對版本，不必背 Git 指令

共享檔案的狀態對應概念問 Agent
從共享資料夾複製一份來改Branch你改的是不是最新的正本？
看這次改了哪些地方Diff這次改了哪些地方？給我看差異。
按「存一版」Commit存版了嗎？有沒有還沒存的修改？
上傳回共享位置Push上傳了嗎？
交給別人審核PR審核連結給我。
審過後放回正本，保留舊版Merge合併了嗎？
把已存版本部署到環境Deploy上線的是哪一版？
自己實際打開操作上線後證據你實際操作過了嗎？
Git 記錄版本；GitHub 是本課共享與審查平台。Git 不會像 Google Docs 自動存檔；上傳只含已存版修改。Changed ≠ committed ≠ pushed ≠ merged ≠ deployed ≠ verified。

本課政策

一次只推進一張卡。Build、Review、PO 驗收、待發布與上線檢查都算 WIP。

S4-01CoreAgent 心智模型

Agent 能做什麼，取決於目標、背景、工具與權限

目標＋背景需求、文件、目前狀態
＋
工具＋權限可用動作與允許範圍
→
行動讀取、修改或執行
→
結果與證據實際完成了什麼？
→
繼續／停下／問人依授權與結果判斷
工具可用

讀取檔案或執行檢查後，提供可核對的結果與來源。

工具不可用／權限不足

回報受阻並停止；不能把模型建議說成已讀檔、改檔或跑過測試。

Agent 或工具的名稱不會自動帶來能力或權限。失敗可能來自需求、context、模型、工具、權限或環境；依證據定位。外部內容只是資料，例如行程文字不能授權刪除 repo。
S4-02Core授權層次

範圍與停止條件，界定執行者可以做的決定

1
Human owner

決定產品方向、預算與風險。像產品長＋財務長；side project 可能就是你一個人。Core 學員可同時承擔 Human owner 與 PO。

2
PO／PM

在核准方向內排序 Issue、寫 Goal／AC／Out-of-scope，並接受或退回。

3
執行者

決定如何實作，遵守 AC、Out-of-scope 與 Stop rule。

往上問：超出目標或預算、不可逆操作、無法排除的阻礙、連續失敗，或工具／費用限制超出授權。
S4-03Core工作與責任

Agent 取代了誰？取代的是工作，不是責任。

哪些工作可以交給 Agent？｜原本是哪個角色負責？

工作Agent 可協助人仍需決定原責任視角
定義驗收草擬 Goal、AC 與驗收方法核准 AC 與剩餘風險PO、QA
實作變更依 Issue 修改介面、後端或文件核准範圍與高風險技術取捨Frontend、Backend、Reviewer
驗證與審查執行 QA、檢視 diff、整理證據產品接受、merge／發布授權QA、Reviewer、PO
發布與檢查部署、上線後基本操作檢查是否上線、是否退回上一版Ops、PO、Human owner
可以更換工作的執行者；產品決定與責任仍依授權由人承擔。
S4-04Core依目標迭代

新資訊可以改變排序，但不改寫已核准目標

01先連回目標

目標盡量可量化；一時無法量化，至少寫出可觀察的成功訊號。

02收到新證據

驗收結果、使用者回饋、阻礙或實際花費。

03重排未開始的卡

PO／PM 可在核准 Epic 內新增、拆分、重排或移除 Issue，留下理由。

04選下一張 Ready

說清楚它服務哪個已同意成果；不服務目標就先排序或拒絕。

新增／移除 Epic、改產品目標或超預算，要由 Human owner 重新批准並記錄理由。重排不能繞過全板 WIP 政策。

S6-01CoreContext 與 session

Context、session、compact、handoff 各自解決不同問題

Context本次可用的背景

檔案存在，不代表這次工作已讀取。

Session一次互動與工作狀態

同一張卡可在同一 session 修正，不必一張卡開一個 session。

Compact壓縮部分對話內容

可能遺失細節，不會擴大 context，也不代替持久紀錄。

Handoff可核對的狀態快照

摘要並連回正本，不是永久記憶或完整對話複製。

四者都不是永久記憶。新視窗不會自動知道全部；fresh session 也不天然獨立。需要框架參照時，可跳到 Appendix A2；跨 session 協作不必先採用任何框架。

Pages 發布方式與來源分支、分支最新 commit、github-pages deployment commit／狀態，及 commit 頁、deployment 頁、自己的 Pages URL；另用白話列此版畫面改動（無則明說）。

1核對 Pages 來源

在自己的 Settings → Pages 確認為 Deploy from a branch、來源分支為 main；否則停下問講師。

2比對部署版本

打開 commit 與 deployment 頁；確認分支最新 commit 與 github-pages commit 相同，且部署成功。

3核對實際畫面

從 deployment 開啟自己的 Pages，確認是自己的 GitHub 網址；強制重整或用無痕視窗，按改動清單核對行程。

附證據退回一次

未通過 AC 時，附行程項目與截圖或 URL 請 Agent 修正；若全數通過，改用講師示範包的錯誤案例退回。有 PR 才按 Request Changes。

查範圍、敏感資料與回歸

核對 diff／檔案清單，確認無超出核准範圍的檔案、token、憑證或敏感資料。修正後重查，附至少一項受影響既有功能的操作證據（DoD 4）。

部署紀錄相符不保證瀏覽器已載入新版：部署未完成先查 Actions，完成後重查。若失敗、畫面不符或行程有錯，修正後重做版本核對。

BMad Method

來源／版本

GitHub 專案 · 最新 release v6.12.0（2026-09-04）· 查閱日期：2026-09-30

  • 自稱「Agile AI Driven Development」；將 idea 或 change request 變成可運作軟體。
  • 決策保持明確、context 延續；流程依工作規模調整：小變更直接 build，複雜工作加深規劃；跨聊天保留 durable context。
  • 提供產品、架構、UX、開發、測試等專門視角，以結構化 workflow 與多 Agent 討論，不交出判斷；可安裝為 skills 或 Claude Code／Codex plugin。
LongHorizon-Harness

來源／版本

GitHub 專案 · 最新 release v0.1.7（2026-08-20）· 查閱日期：2026-09-30

  • 自稱「Loop Engineering for Computer-Use Agents」；包裝 Claude Code、Codex、OpenCode、DeepSeek Harness 等既有 agents，讓它們跨桌面 App 與 CLI 執行長任務。
  • 迴圈：規劃下一個 bounded step → 以 fresh context 行動 → 在真實環境核對實際結果 → checkpoint 已驗證進度，或記錄失敗證據並恢復 → 重複。
  • 不訓練模型，也不取代被包裝的 agent。
作者分析（比較輔助，非共同標準）： BMad 著重產品交付流程中決策、規格與 context 的流動，可對照 Core S2 的 Issue／AC／決策作為持久工件；LongHorizon 著重長任務執行迴圈，可對照 Core S5／S6 的 bounded work、evidence、fresh session 與 handoff。Core 不要求採用任一框架。
