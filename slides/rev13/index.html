軟體專案靠人、流程、文件與版本管理一起推進。

四個位置各自負責不同工作，GitHub 把工作紀錄和版本審查連起來。

講者筆記

Data：同一個工作會經過多種職能與階段，並留下文件和版本紀錄。

Insight：文件說明做什麼、為什麼與如何驗；版本管理回答哪一版、由誰改及如何整合。

Go：先請學員指出四個固定區域，再帶到下一張同一張圖的變化。

Evidence scope：課程概念圖；沒有宣稱任何票、分支或版本已建立。

下一站：在相同座標加入 Agent 第五層，原四區不移動。

加入 Agent 後，四個基礎與人的決策責任仍在。

Agent 可以受委派執行或協調工作；範圍與最後決策仍由人負責。

講者筆記

Data：四個基礎區域、角色、流程位置與文件／版本關係和前一張一致；只揭露 Agent 層。

Insight：Agent 改變執行或協調者，不取代文件、版本管理、授權邊界或 Human Gate。

Go：用方向鍵揭露第五層，請學員確認原四區仍在原位。

Evidence scope：教學模型，不代表已執行 Agent 工作。

下一站：沿同一張 Process 區分七個看板狀態、活動與欄外決策。

工作流程有七個看板狀態，活動與欄外決策各有位置。

Brainstorming 與 Refinement 是活動，Human Gate 是 Product Check 後的欄外決策。

講者筆記

Data：看板依序是 Backlog、Ready、Dev、Review、QA、Product Check、Done。

Insight：Refinement 在 Backlog 進行；Human Gate 是 Product Check 後的授權決策，不是第八欄。

Go：沿七欄讀一次，再指出活動帶與欄外 Gate。

Evidence scope：概念流程圖；沒有表示任何票實際移欄。

下一站：學會讀一張 Stage Card 的欄位。

Stage Card 分開說明產品目標、本站任務和接手條件。

產品 Goal 描述結果，Stage Target 描述本站任務，Exit Criteria 決定是否能交棒。

講者筆記

Data：Stage Card 會交代 Product Goal reference、Target、Input、Activities、Output、Exit、People、Current State 與 GitHub mapping。

Insight：Goal 是產品結果；Target 是本階段工作；Exit Criteria 是下一站能否接手的條件。

Go：請學員從 Input 沿活動與 Output 讀到 Exit，再看角色和 GitHub 對應。

Evidence scope：欄位解說，非實際票面或流程進度。

下一站：認識角色是責任，不是人數。

角色代表責任，一個人可以承擔多個角色。

Role 是工作責任，角色數不等於團隊人數或 Agent 數量。

講者筆記

Data：Owner、PM、PO、UI/UX、Dev、Reviewer、QA 是本課使用的職能。

Insight：職能描述誰承擔決策或工作，不規定團隊必須有幾個人或 Agent。

Go：請學員挑一個角色，說出它負責的工作，不先推定人數。

Evidence scope：角色模型；不代表固定組織編制。

下一站：把主責與協作角色放到各工作階段。

每個階段都有主責、協作與決策角色。

主責者承擔本站結果，協作角色按需要加入；責任不代表固定人頭編制。

講者筆記

Data：Owner 主責方向與 Human Gate；PM 主責 Brainstorming／Refinement；PO 主責 Refinement、Ready 與 Product Check；UI/UX 視需要協作；Dev、Reviewer、QA 各有實作、審查與驗證責任。

Insight：矩陣表達本課示範的責任分布，不是固定人員配置；Developer 自述不取代獨立 QA 證據。

Go：沿一個階段追到主責角色，再辨認其協作者。

Evidence scope：課程責任模型。

下一站：看工作文件如何從 Goal 分解並留下驗收契約。

工作文件從 Goal 延伸到票、驗收條件與完成定義。

Epic、Story、Task 是團隊可選的工作分類；GitHub Issue 承載工作紀錄。

講者筆記

Data：Goal／Proposal 說明為何做；Epic、Story、Task／Ticket 將工作切成可交辦範圍；Scope、AC、AT、DoD 說明要做什麼、怎麼驗與共同完成條件。

Insight：Epic／Story／Task 是課程採用的分類方式，不是每個 GitHub repo 的內建固定類型。

Go：從 Goal 沿分解關係讀到工作票，再追到 AC 與驗收材料。

Evidence scope：文件概念圖，沒有建立任何 Matching Issue 或 AC。

下一站：追同一份文件如何跨工作階段更新。

同一張 Issue 沿流程補充工作契約，並連結其他紀錄。

示意：Issue 保留工作契約，PR 與 Evidence 指回候選版本及實際檢查。

講者筆記

Data：Goal／Proposal 在 Brainstorming 開始；Parent／Child Ticket 與 AC、AT、DoD 在 Refinement 形成並在後續站點使用；Review／Test Evidence 連到候選版本；Go/No-Go 與 Release 記錄由授權流程形成。

Insight：Issue、Project、PR 可承載協作內容，但不是 Git Commit；GitHub 連接工作紀錄和版本審查。

Go：沿文件連線找建立、更新、審查與留存位置。

Evidence scope：生命週期示意，不代表文件已建立或已更新。

下一站：分清各種目標、條件與證據的適用層級。

Goal、Stage Target、AC、AT、DoD 與 Exit 各自回答不同問題。

Goal、Stage Target、AC、AT、DoD、Exit Criteria 與 Evidence 分別約束不同範圍。

講者筆記

Data：Goal 是產品 Outcome；Stage Target 是本站工作；AC 描述工作範圍內的行為；AT 是檢查情境；Exit 決定交棒；DoD 是共用完成條件；Evidence 記錄實際觀察。

Insight：一個層級的 PASS 不會自動證明其他層級完成。

Go：請學員把一個問題放到能回答它的層級。

Evidence scope：術語邊界概念圖；未展示 Matching 測試結果。

下一站：辨認 Git、GitHub 與各協作物件。

Git 保存版本歷史，GitHub 連接工作票與程式送審。

Git 管版本歷史；Issue 與 Project 管工作和狀態，PR 連起票與版本差異。

講者筆記

Data：Git 管版本歷史；Repo 容納受版本控制的檔案；Branch／Commit 表示隔離修改與歷史節點；Issue／Project 記工作與狀態；PR 承載版本送審、討論與 Checks；Merge 整合獲准變更。

Insight：GitHub Issue 不是 Git Commit，PR 也不是 Ticket；PR 是文件討論與版本差異交會的位置。

Go：請學員沿工作紀錄軌和版本軌，指出兩軌在哪個協作物件相連。

Evidence scope：物件關係概念圖，沒有建立真實 Repo、Branch 或 PR。

下一站：把版本變更讀成可回查的分支路徑。

分支、提交、PR 與 Merge 留下可回查的版本路徑。

Branch 隔離修改、Commit 留下節點、PR 請人審查，Merge 才整合變更。

講者筆記

Data：一條抽象版本路徑從 Repo 的既有版本分出 Branch，Commit 記下修改，PR 呈交差異供審查，經授權後才 Merge。

Insight：版本路徑可以比較、回查與回復；PR 開啟或審查通過都不等於已 Merge。

Go：沿路徑指出哪些物件代表隔離、記錄、審查與整合。

Evidence scope：版本歷史示意，不對應 Matching Version A/B 或真實 PR。

下一站：認識 Agent、Session、Chat 與 Workflow 的差別。

Agent 能在受委託範圍內執行，但不能替人決定放行。

本頁只預告工作情境；五項守則會在後半的實作案例中完整示範。

講者筆記

Data：Chat 是互動介面；Session 是一次工作脈絡；Agent 是能依指示使用工具的執行者；Workflow 是多步工作流程。

Insight：這些名詞不互相等同。Agent 可讀取指定工作契約、在授權範圍內執行並回報；範圍改變與最後放行仍由人決定。

Go：指出一個可能受委託的工作，並追問其工作票、驗收條件與停止點。

Evidence scope：概念預告；不表示已執行單 Agent／多 Agent 工作，也不展示測試結果。畫面只留一行情境預告：「有人想做配對」。

下一站：使用已學的角色、文件與 GitHub 名詞讀 Brainstorming Stage Contract。

Brainstorming 先把問題整理成共同方向。

本站結束要留下可回查的 Goal／Proposal，方向仍由人確認。

講者筆記

Data：Target 是決定下一個要處理的使用者問題與方向；Input 是問題、觀察、機會與限制；活動包含探索選項和成功訊號；Output 是 Goal／Proposal 與未決假設。

Insight：產品 Goal 尚待形成；沒有方向確認與共同紀錄，就不能假設工作已 Ready。

Go：先找出誰確認方向，再追到 Goal 或 Proposal Issue 的記錄位置。

Evidence scope：Stage 定義；沒有 Matching 決議或 Issue 建立事件。

下一站：在 Backlog 的 Refinement 把方向變成可交辦工作。

Refinement 把 Goal 拆成可估算、可驗證的工作。

票可以拆分並釐清，仍要符合 Ready 條件才可接手。

講者筆記

Data：Input 是已決定的 Goal、限制、依賴和未決問題；活動包括界定範圍、拆 Epic／Story／Task、釐清 AC／AT、證據、風險與負責角色；Output 是 Parent／Child Tickets 及未決清單。

Insight：Refinement 在 Backlog 進行，拆票完成不會自動把票移到 Ready。

Go：檢查是否仍有阻礙；處置未決項後，再由 Ready Check 判定能否接手。

Evidence scope：Stage 定義；沒有宣稱 Matching 子票或 Project 欄位已建立。

下一站：Ready Check 確認這張票是否具備開工條件。

Ready 確認工作契約可接手，仍然尚未開工。

符合本課 Ready 條件後才能拉進 Dev，開工前 WIP 仍為零。

講者筆記

Data：PO／Dev 主責確認；QA 協作檢查範圍、AC、可測性、依賴與責任；Output 是可接手的 Ready Ticket 與明確接手者。

Insight：Ready 是允許開始工作的條件，不代表已經開始或已完成測試。

Go：逐項核對 Required Ready 條件，再判斷是否允許拉進 Dev。

Evidence scope：Stage 定義；畫面上的 Backlog／Ready 是流程說明，不是某張真實票的狀態。

下一站：Dev 在核准範圍內產生候選版本與自測紀錄。

Dev 在核准範圍內實作並交出候選版本與自測紀錄。

自測紀錄能交給審查者參考，但不等於獨立 QA 完成。

講者筆記

Data：Input 是 Ready Ticket、設計／AC、共同 Repo 與 Stop Rules；Dev 建 Branch、修改、Commit、自測並記錄未完成項；Output 是候選版本、修改摘要與自測紀錄。

Insight：候選版本需能對回核准票；Developer 自測不替代 Reviewer 或 QA 的獨立責任。

Go：確認交接內容包含修改版本、自測範圍與未驗項，再進 PR Review。

Evidence scope：Stage 定義；沒有展示實際 Matching 版本或測試結果。

下一站：Reviewer 比對 PR 差異與工作契約。

PR Review 檢查程式差異是否符合票與範圍。

Reviewer 的意見要有處置，PR 尚未合併時仍是候選變更。

講者筆記

Data：Reviewer 讀 PR diff、Ticket／AC、版本與自測摘要，留下 findings、approved 或 changes requested。

Insight：PR Review 查改動、範圍與風險；它不取代依 AC 執行的 QA，也不表示已 Merge。

Go：先處置重大意見，確認候選變更可交付 QA，再交接測試證據。

Evidence scope：Review 站定義；沒有虛構任何真實 PR 歷史。

下一站：QA 用可重跑的方式核對候選版行為。

QA 對照可識別的候選版本與 AC，留下測試證據。

每個結果都要連到實際執行的案例、預期、觀察與候選版本。

講者筆記

Data：Input 是候選版本、AC／AT、測試資料與環境；QA 記錄預期與實際，標示 PASS、FAIL 或 NOT RUN；Output 是可追溯的測試紀錄與補驗請求。

Insight：沒有執行的案例保持 NOT RUN；結果只支持它實際檢查的版本與範圍。

Go：核對結果是否可重跑、版本是否一致、未測項是否清楚，再交給 Product Check。

Evidence scope：QA 方法概念；不展示 Matching A/B 結果，UI、E2E、Release 與 Goal 測試若被提及皆為 NOT RUN。

下一站：PO 對回 Parent Goal，判斷單票和產品方向。

Product Check 核對這張票是否仍推進產品目標。

接受或退回的是目前這張票的範圍與證據，不是整體 Goal 成效。

講者筆記

Data：PO 主責，Owner、Dev、QA 視需要協作；依 Ticket／AC、Review／QA Evidence、Parent Goal 與風險，記錄接受範圍、退回理由或未完成產品路徑。

Insight：單票符合需求不等於整體產品 Goal 已達成；保留未解風險與相關票的依賴。

Go：把結果對回 Parent Goal，決定接受、退回或需要人類授權。

Evidence scope：Stage 定義；沒有宣稱產品成效已測量。

下一站：授權者在看板欄外作 Human Gate 決策。

Human Gate 是欄外的人類授權，不是第八個看板欄。

授權、暫停或退回都要留下紀錄；授權本身不會自動完成 Merge 或 Release。

講者筆記

Data：Owner 或有權決策者主責；輸入是候選版、Review／QA Evidence、剩餘風險與發布計畫；輸出是可回查的授權、暫停或退回決策。

Insight：Human Gate 位於 Product Check 後、Done 前的看板欄外；Agent 不自行取得放行權。

Go：先檢查證據與風險，再辨認決策人和後續 DoD 條件。

Evidence scope：授權流程定義；沒有任何真實放行決議或 Merge。

下一站：確認 Merge／Release／Done 各自需要哪些實證條件。

Merge、Release 與 DoD 證據齊備後，票才可標記 Done。

規則層測試通過不能替代整合、上線檢查或整體 Goal 衡量。

講者筆記

Data：Dev 依已授權候選與 Release／DoD Checklist 整合、發布並留下交付證據；Output 包括 Merged Commit、Release 記錄與 Issue／Project Done（僅在證據成立時）。

Insight：QA PASS 不能自動替代 Human Gate、Merge、Release 或 DoD；單票完成和整體 Goal 成效分開衡量。

Go：逐項確認是否真有授權、Merge、Release 與可檢查的 DoD 證據。

Evidence scope：條件式 Stage 定義；本課 Matching UI／E2E／Release／Goal 測試未執行時必須標示 NOT RUN。

下一站：以一張教學示意卡進行 Part 1 Exit Check。

面對一張陌生工作票，你能指出誰接手與下一步嗎？

先讀票面事實並作答，再展開參考判斷；不是 Matching 測試結果。

講者筆記

Data：學員先閱讀工作票標題、描述、既有 AC、目前看板欄與兩則留言，再回答 Goal、本站工作、AC／留言、People／Exit 與 GitHub／版本問題。

Insight：能讀出一個欄位還不夠；要能把票、負責人、候選版本、Evidence 與下一站連起來。

Go：先讓學員口頭或筆記作答，再逐題按方向鍵揭露參考判斷；畫面只保留正在討論的一題答案。

Evidence scope：概念練習；Stage Card 明示為教學示意，不展示 Matching A/B 實測結果。真人學員試教尚未執行。

揭露節奏：先請學員自行記錄五題答案，再依序前進五個 fragment；每次只顯示當前題目的參考判斷。
