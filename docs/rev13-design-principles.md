# Rev13 投影片設計原則（最高優先）

> **優先順序：本文件 > AGENTS.md 其他段落 > v5／v4 Storyboard、Visual Contract、Manifest、Gates 等所有規格。**
> 規格決定「教什麼內容、證據範圍」；本文件決定「怎麼呈現、用什麼字」。兩者衝突時以本文件為準，並回頭修正規格。
> 來源：Owner 歷次指示（原話紀錄於 Issue #41、#60 與審查紀錄），以及下列三位作者的原則。

## 1. Owner 原則

### 受眾與敘事
1. **面向零基礎學員**（可能非工程師）。不增加認知負荷：**禁用內部代號**、不用自創術語；每個術語先教後用。
   - **內部代號一律不得出現在任何給人看的地方**（畫面、講者筆記、PR／Issue 說明、對 Owner 的回報）：scene ID（O01、C11、A06…）、批次名（B1、B2…）、證據資料夾名（`B-pre-supplement` 等）、版本代號（Version A、B-pre、B-post）、SHA、檔案路徑代號。
   - 指稱頁面時用「第 N 頁（標題）」；指稱證據時用白話：第一版／修正版・第一次測／修正版・補測／重複按讚／未測。
   - 內部代號只可留在機器欄位（`data-*` 屬性、manifest、檢查器），學員與 Owner 看不到的地方。
   - 規格名詞要先通過本條，才可以上畫面。
2. **主軸**：先人類團隊怎麼做軟體（人、流程、文件、版本管理），再 Agent 接手人的工作。Part 1 認識地圖；Part 2 用同一個案例走完整個流程。
3. **標題就是該頁內容**：一句完整的話或問題，不是章節名。
4. **漸進式揭露：先講大重點，再一個一個展開**（Owner 2026-10-15）：開場先只給四大重點的空骨架，下一頁才加 Agent，之後每頁只展開一個要素的一部分；不可第一頁就放完整細節再分批點亮。工作階段同理：全貌 → 聚焦 → 本站工作與產物 → 回到全貌看變化。
5. **以配對交友 App 的「配對功能」為例**（兩人互相按讚才配成一對；Owner 2026-10-15），只完整走「配對規則」這一張票（lead by example），開頭即說明其他票、介面、上線不在範圍。Part 1 只介紹工作站，不先演 Part 2 的測試結果。**Agent 章不倒帶**：人類流程走完後，另開一章「同一張票交給 Agent 再走一次」，從頭往前，五項原則在發生的那一站出現；Agent 版是教學示意。
6. **極簡版面**：每頁只有標題＋一張主圖＋≤2 句。不要 eyebrow／kicker、頁 ID、scene ID、tier chip、角落小字。
7. **不寫分鐘數或總長度**；時間由 Owner 依場合控制。

### 視覺
8. **一張母圖＝data-flow 圖**（Owner 2026-10-15 定；參考 cathrynlavery/diagram-design `data-flow.png`，最新參考取代先前的泳道圖、泳道流程圖）：
   - **上方編號步驟列＝流程**：01 想法 → 02 拆票 → 03 可開工 → 04 實作 → 05 審查 → 06 測試 → 07 對照目標 → 08 人決定 → 09 完成；當前步驟亮起。「人決定」用與其他步驟不同的樣式標出它是人的授權，不是看板欄。
   - **左側角色列＝人**：一個角色一列；Agent 是第 2 頁才新增的一列。
   - **卡片＝事情**：左上角色小標、主文字「做什麼」、一行「輸入 → 產出」；**左下＝輸入標籤、右下＝產出標籤**。標籤兩種顏色：**文件類**（目標、工作票、驗收條件、測試紀錄、放行紀錄）與**版本類**（Branch、Commit、PR、Merge）＝文件與版本管理。
   - **連線**：一般交接、本頁重點交接（強調色，每頁 1 條）、退回（虛線）。不用判斷菱形、不圍框。
   - **底部說明三列**：步驟／標籤類型（文件、版本）／連線。
   - 不再有四大框、文件軌、版本軌。
9. **聚焦用遮罩**，不刪除非焦點元素，學員永遠知道自己在哪。
10. **回到全貌一定看得到變化**（開 Issue、拆票、移欄、測試結果，前後對照）；不可重貼沒變化的全貌。
11. **關係要畫出來**：誰、在哪站、用哪份文件、對應哪個版本，用連線或位置表現。
12. **外部參考圖重畫並標出處。**
13. **視覺品質以得獎作品為目標**：線不穿字、箭頭不擠、字在投影距離可讀（主內容 ≥22px、次要 ≥16px，1440 寬基準）。
14. **原生可編輯元素**：HTML／PPTX 不得把整頁或主圖做成圖片。

### 內容真實性
15. **不捏造**：示意標「示意」。真正實測只有規則層三步：第一版 FAIL → 修正版第一次測（單向、雙向 PASS；重複按讚未測）→ 修正版補測（重複按讚 PASS，同一份修正版程式）。介面、端到端、上線、整體 Goal 一律「未測」。
16. **Rev12 五項 Agent 協作原則保留在主線**：External Task State、Bounded Execution、Role Separation、Independent Verification、Goal Re-anchoring。
17. **不可混淆**：角色 ≠ 人數 ≠ Agent 數；文件（做什麼、怎麼驗）≠ 版本管理（哪一版、誰改）；GitHub ≠ Git；看板七欄，Brainstorming／Refinement 是活動，Human Gate 是欄外人類決策。

### 審查流程
18. 每批實作完成先做**小白讀**：只看投影片、不看規格，從頭讀到尾；抓順序、先用後教、跳太快、矛盾、看不懂的詞、負擔過重。
19. 審查不能只對照規格；必須同時對照本文件，規格有錯要指出。
20. **最新參考取代舊參考**：Owner 最新肯定的參考圖就是唯一基準；不疊加、不投票推翻；換基準時整張重做並列出拿掉的舊元素。

## 2. 三位作者的原則（本課轉譯，非原作者提出此課程分類）

| 作者 | 原則 | 本課套用 |
|---|---|---|
| **林大班**（BFA） | **Structure**：分類分段、閱聽人角度、視覺一致。**DIG**（Data → Insight → Go）決定每頁讓人看懂什麼；**FIG**（Font／Ink／Grid）安排主次。 | 每頁先定學習任務再排版。Part 1 與 Part 2 視覺目的不同，不重講同一內容。 |
| **Ben Shneiderman** | 資訊探索七項任務（*The Eyes Have It*, 1996）：Overview、Zoom、Filter、Details-on-demand、**Relate**、**History**、Extract。Eight Golden Rules：一致性、回饋、完成感、可回頭、掌控感、**減少短期記憶負擔**。 | 同一張母圖先全貌再聚焦；畫出人↔流程↔文件↔版本關係（Relate）；回全貌看得到前後變化（History）；全份同一套符號。不要機械地每頁塞七項任務。 |
| **Richard Mayer** | **Pre-training Principle**：學複雜系統運作前，先學會主要組件的名稱、特徵與角色。 | Part 1 的理由：先認識角色、文件、Git／GitHub、Agent，Part 2 看流程時不用邊看邊猜名詞。 |

**圖法參考**：泳道、看板、樹、時間線與連線規則參考 [cathrynlavery/diagram-design](https://github.com/cathrynlavery/diagram-design)（MIT），維持本課深色主題，重畫不複製。

**出處註記**：BFA「分鏡溝通法／半透明遮罩」文章作者為**魯蓓蓓**，不得標成林大班原創。詳細來源見 [研究筆記](rev13-presentation-research-lin-shneiderman.md)。
