# Agent 101 講師指南

本指南配合合併版 `slides/index.html` 與 `docs/v6-storyboard.md`。依 S0–S7 順序教學；Core 是主線判斷，講法可以精簡但判斷不可刪。Optional 可略過而不影響 Core；Appendix 僅供查閱。

依 D5（#25）原則，課堂內容取捨由講師依現場時間控制；不得把 Optional 或 Appendix 升格為 Core。

下列 Core／Optional／Appendix 標示附在內容單元名稱上；括號中的 slide ID 僅供定位。

## S0｜課程定位

**目標**：先建立軟體交付流程，再談 Agent 可承接哪些有界、可驗收的工作。完成須有條件與證據，不能由 Agent 自述、merge、Issue 關閉或部署單獨決定。

**先備概念**：無。可用學員熟悉的產品功能說明需求、修改、檢查和交付。

**示範步驟／工件**

1. 用 **S0-01** 說明本課不要求手寫程式，也不承諾把人變成後端工程師或保證產品成功。
2. 用 **S0-02** 沿需求／目標、Issue／AC、實作、QA、Review、PO 接受、授權發布、上線後檢查走一遍；指出退回修正、Blocked 與另立需求的返回路徑。

**要問學員的問題與預期判斷**

- 「Agent 說完成、Issue 關閉、PR merge 或網站已部署，哪一個足以判定 Done？」預期：都不足以單獨判定。須有 PO 對應候選版本依 AC 接受，且適用的 DoD 證據齊全。
- 「基本操作能用，是否表示每條 AC 都通過、產品目標也達成？」預期：不表示；逐條核 AC，目標成效另看可觀察訊號。
- 「QA 或 Review 未通過、新資訊形成另一個需求，下一步呢？」預期：原卡回修並重驗；Blocked 留原因與下一位處理者；新需求交 PO 判斷是否另開 Issue。

**常見誤解與救援**：若學員把「網站打得開」當作 Done，請他指出 AC、候選版本、Review、發布授權和上線後證據各在哪裡；缺少就先不標 Done。全班答不出時，依序提示「要證明哪條 AC？對應哪個候選版本？由誰接受？還缺哪項證據？」，最後讓學員依缺項判斷尚不能標 Done。

**內容單元層級與伸縮**

- **Core｜課程定位（S0-01）**：壓縮時保留「軟工流程在前、Agent 承接有界工作」和課程承諾界線；展開時請學員說出自己工作中誰定目的、誰執行、誰接受。
- **Core｜交付全貌（S0-02）**：壓縮時沿流程圖指出接受、發布、檢查與返回箭頭；展開時用一個 QA 退回和一個新需求情境讓學員排出正確下一步。

**講師備註**：本課所說「完成」是有條件的交付狀態。部署、對使用者開放、GitHub Release 與 merge 是不同事件；依本卡適用的流程說清楚，不要用它們互相代稱。

## S1｜軟體工程與角色

**目標**：用同一個 Matching 例子說明產品行為由介面、後端規則、資料和多種責任共同完成；把工作拆成 Epic 與可驗收 Issue。

**先備概念**：理解 S0 的目標、流程與接受責任；無須有程式經驗。

**示範步驟／工件**

1. **S1-01**：畫出 A 喜歡 B、B 也喜歡 A 才建立配對；指出介面、後端判斷與保存資料各自承載的事。
2. **S1-02**：沿同一需求逐一看 PO、Frontend、Backend、QA、Reviewer、Ops 的責任與問題。
3. **S1-03**：看 Matching Epic 下的一張 Issue；對照 Goal、情境 AC、GitHub Project 與 Epic。
4. **S1-04**：對照 Sprint 的固定週期與本課 Kanban 的持續流動及回饋。

**要問學員的問題與預期判斷**

- 「這個需求現在是 PO、FE、BE 還是 QA 的哪種問題？」預期：按責任判斷，而非按人名或職稱猜。PO 確認為誰解決什麼、怎樣算符合；FE 處理操作和呈現；BE 處理身分、資料、API 和規則；QA 查行為及失敗路徑。Reviewer 查變更、範圍和風險；Ops 查發布、環境、運行和恢復。
- 「A 喜歡 B，B 尚未回應，是否成立配對？」預期：否；雙向喜歡才成立。C 單向喜歡 B 也不成立；若 C 讀取 A 的 Match，應依情境拒絕存取。
- 「Goal 寫什麼、AC 怎樣寫？」預期：Goal 用一句話說明為誰、為什麼；AC 寫可觀察情境，例如 A/B/C 的選擇、結果和拒絕路徑。
- 「GitHub Project 和 Epic 是同一個東西嗎？Kanban 是否要求 User Story 格式？」預期：不同；Project 用來整理追蹤工件，Epic 是本課的大工作分組。Kanban 不規定工作項目格式；User Story 起源於 XP，Scrum 與 Kanban 都不要求一定寫成 User Story。
- 「PO、PM、Scrum Master 是可互換的職稱嗎？每種責任必須由不同人擔任嗎？」預期：不可互換；責任視角不代表組織必須設同名職位或一人一職。
- 「Sprint 是本課工作流程的必要前置嗎？」預期：不是。本課採 Kanban；Sprint 只作節奏與回饋方式的對照，不教 Scrum 儀式。

**常見誤解與救援**：若討論滑向組織職稱或 User Story 範本，回到 Matching 卡上的 Goal、AC 與待回答問題；若把 Project 當 Epic，請學員指出哪個是追蹤工件的地方、哪個是工作分組。全班答不出時，依序提示「A、B 各做了什麼？產品規則要求什麼結果？哪種責任視角要處理？哪張 Issue／哪條 AC 能驗證？」。

**內容單元層級與伸縮**

- **Core｜Matching 產品行為（S1-01）**：壓縮時保留雙向規則與前後端分工；展開時依序追問介面、規則、資料與失敗情境。
- **Core｜六種責任視角（S1-02）**：壓縮時只用六列責任表；展開時讓學員將新情境歸給責任視角並說明依據。
- **Core｜Epic、Issue、Goal 與情境 AC（S1-03）**：壓縮時保留 Epic → Issue、Goal、情境 AC、Project ≠ Epic 和界線句；展開時讓學員口述 A/B/C 的預期結果。User Story 詞條只在 **A1 Appendix** 查閱。
- **Core｜Sprint／Kanban 節奏對照（S1-04）**：壓縮時只比較固定週期與持續流動；展開時討論回饋如何影響下一張 Ready 卡，不加入 Scrum 儀式清單。

**講師備註**：Epic → Issue 是本課採用的兩層拆法，不是 Kanban 或 GitHub 的普遍規定。角色是責任視角，不應講成固定職位或 Agent 名稱的對等映射。

## S2｜工作怎麼流動

**目標**：把模糊要求整理成授權邊界，分清 AC 與 DoD，並依候選版本與證據走完驗收、接受、發布和檢查。

**先備概念**：S0 的交付全貌；S1 的產品行為、責任與情境 AC。

**示範步驟／工件**

1. **S2-01**：從 Matching Issue 圈出 Goal、AC、Out-of-scope、Stop rule，指出哪裡要先問 PO。
2. **S2-02**：先問「做對了嗎？」（AC），再問「收尾了嗎？」（DoD），逐條查看本課 DoD 四項與三張反例卡。
3. **S2-03**：走完 AC 約定 → 實作 → QA → Review → PO 接受候選版本 → 授權發布 → 上線後檢查 → Done；示範 Comment、Approve、Request Changes 的差別。
4. **S2-04**：逐條讀一張 AC 證據卡，核對方法、預期／實際、狀態、版本／環境與連結。
5. **S2-05**：用共享檔案比喻走過八個版本核對問題；請學員實際開啟 Agent 提供的連結。

**要問學員的問題與預期判斷**

- 「Agent 順手替 Matching 加聊天室，但 Issue 沒有批准，怎麼處理？」預期：Request Changes；未授權部分不能因為可用就併入，另拆新卡交 PO 判斷是否做。
- 「AC 寫了什麼，什麼情況要 Stop？」預期：AC 是單卡可觀察行為；若需要新增資料、改授權、超目標／預算、遇不可逆操作、反覆失敗或無法排除阻礙，停止並往上問。
- **反例一：符合 AC、DoD 未完成**——配對只在 Agent 環境跑起來，PR 未審且未發布。預期判斷：不可 Done；缺 Review 與適用發布／上線後檢查證據。救援：讓學員在四條 DoD 中指出未過項，不接受「Agent 已完成」作證據。
- **反例二：DoD 看似通過、AC 未通過**——已審查、已發布、基本操作可用，但 B 尚未 Like 就成立 Match。預期判斷：不接受；產品行為違反 AC，即使流程收尾也不是正確交付。救援：回到該 AC 的操作情境重驗。
- **反例三：AC 與部分收尾都過、但超出核准範圍**——Agent 多做聊天室等功能。預期判斷：Request Changes；範圍不符，拆成新卡讓 PO 決定。救援：以 diff 對照 Out-of-scope，說清楚超出的檔案／行為及其風險。
- 「DoD 四條各是什麼？PO 接受前要確認哪些？」預期：①PR 審查通過且阻擋已處理；②上線後基本操作通過並附版本／操作證據；③沒有超出核准範圍；④受影響既有功能檢查通過並附證據。PO 接受前確認 1、3、4；授權發布後補 2；全部 AC 獲 PO 接受且四條 DoD 全過才 Done。
- 「QA、CI、Review、PO 接受各自做什麼？」預期：QA 查行為與失敗路徑，CI 只是其中一種證據；Review 查 diff、範圍和風險；PO 在能對應候選版本的驗收環境依 AC 接受。Review 核准本身不授權 merge 或上線。
- 「Comment、Approve、Request Changes 各代表什麼？」預期：意見／提問、Review 結論、要求修正。QA／Review 可以依 AC 或 DoD 退回。
- 「測試沒跑卻報成功，應標什麼？」預期：NOT RUN，不能當 PASS。救援：請學員打開測試紀錄，自己指出缺少執行與結果證據；要求補跑並重新核對，無法執行就保持 NOT RUN。
- 「驗收頁仍顯示舊版，能證明候選版通過嗎？」預期：不能；先核對目前頁面及版本是否對應候選版，修正或部署完成後重驗。尚未授權上線時正式站仍是舊版可能完全正常，不能只因正式站未變就判假完成。救援：請學員比對頁面與候選版本，自己指出缺少哪項版本／畫面證據並要求補驗；先確認該環境是否已獲授權發布。
- 「Review 發現測試被刪除、跳過或改弱，該怎麼辦？」預期：檢查測試變更與批准依據；未釐清前不接受綠燈，要求補回／補證據或按核准需求修正。救援：請學員從 diff 指出測試變更，再找出支持該變更的需求與批准依據；沒有依據就要求補回或補證據。
- **#16 §11 PR 證據互動**：「這份 evidence 能證明什麼、不能證明什麼、還缺什麼？」預期：只認它實際覆蓋的行為、版本與環境；學員自己指出缺少的操作、版本或檢查證據，並要求補驗，不能只看紅字選答案。救援：先讓學員逐項對照 evidence、行為、版本與環境，再請他說明哪項主張尚無證據並提出補驗要求。高風險資料、授權、付費或不可逆改動要找具能力者做技術審查；技術審查與有權者接受剩餘風險是兩個決定。
- 「你改的是不是最新的正本？實際改了什麼？存版、上傳、送審、合併、部署了嗎？你實際操作過嗎？」預期：逐步核對狀態並打開連結；`changed ≠ committed ≠ pushed ≠ merged ≠ deployed ≠ verified`。

**常見誤解與救援**：網址存在不等於候選版本正確；CI 綠燈不等於 AC 通過；Review 核准不等於發布授權；部署不等於使用者已看到該版；一張漂亮截圖不替代逐條 AC 證據。救援時請學員指出「這項證據對應哪條 AC、哪個版本、哪個環境」，再決定補驗、退回或標記 BLOCKED。這裡不要求非工程師讀懂全部測試；要求學員自己指出缺少哪項證據並要求補驗。若測試有合理更新，須有需求與批准依據。

**內容單元層級與伸縮**

- **Core｜工作卡與授權邊界（S2-01）**：壓縮時只保留四個授權欄位及 scope creep 問題；展開時讓學員將模糊需求改成 Goal、AC、Out-of-scope、Stop rule。
- **Core｜AC、DoD 與三個反例（S2-02）**：壓縮時保留 AC／DoD 兩問、四條 DoD、Done 條件和三個反例的判斷；展開時逐條補上證據欄位。
- **Core｜驗收與發布階梯（S2-03）**：壓縮時保留驗收階梯、三種 PR review 動作和「審查不等於授權」；展開時讓學員指出失敗後退回哪一關。
- **Core｜逐 AC 證據（S2-04）**：壓縮時逐例問「證明什麼、缺什麼」；展開時由學員自己填逐 AC 證據欄。完整追溯表是 Advanced／O1 的延伸，不作 Core 前置。
- **Core｜版本狀態核對（S2-05）**：壓縮時保留八個問句與狀態界線；展開時打開 Agent 提供的實際連結核對。`revert`、部署 `rollback` 和資料恢復見 **O1 Optional**。

**講師備註**

- **調查卡例外（D2＝#22）**：完成條件是事先約定的問題有答案、結論有依據；若無法下結論，要交代原因與未解問題。調查卡不必硬做成產品 PR、部署或 Release。一卡一小 PR 只是方便檢視差異與證據的教學約定，不是 GitHub 限制。
- **講師備課檢查**：逐一確認 Core 三個證據反例（測試未執行卻報成功、驗收頁仍是舊版、測試被刪除／跳過／改弱）可由課堂使用的證據或畫面重現，並能展示各自應有的判斷。對非 Travel Lite 的示範 repo，核對 merge／deploy 授權與該 repo 的 GitHub 設定一致；這項設定核對不適用 Travel Lite（學員自己的 repo）。
- **通用「發布前接受」概念**：在能對應候選版本的驗收環境依 AC 接受，再依授權發布；不要把驗收定義成某一種預覽產品。
- **Travel Lite 的實際環境**：依 #22 owner 決議，學員自己的 GitHub Pages 練習站就是驗收環境。早期「PR preview 先實測」已被此決議取代；練習站只有學員自己看，第一版從零做出，沒有要保護的其他使用者或上線前後切換，所以不做 PR preview。PR preview 的實作放 Advanced #18，以 Vercel 內建功能示範。
- **D4（#24）術語對照（講師備註，不要求學員背）**：`working tree`／status 是本機工作副本及尚未存版的變更；`diff` 是本次實際差異；`staging` 是挑入下一次 commit 的變更集合，交由 Agent 處理，Core 不教也不要求學員判斷；`remote sync` 是核對本機副本與共享遠端狀態，修改前確認正本沒有更新、上傳後確認共享位置狀態。學生學的是白話問句與打開連結核對，不是指令。
- Merge、部署、對使用者開放與 GitHub Release 分開講。Git 記錄版本，GitHub 是本課共享與審查平台；Git 不像 Google Docs 自動存版，merge 後舊版本仍在。

## S3｜Kanban 共用協作面

**目標**：使工作狀態可共享，讓需求、變更、證據和持續有效知識各自回到正本；遵守本課全板 WIP=1。

**先備概念**：S1 的 Issue／Epic 和 S2 的驗收流程、S2-05 的版本狀態。

**示範步驟／工件**

- **S3-01**：沿 Board、Issue、PR、README／現行文件指出各自承載的資訊，再以狀態只在 Slack／Chat 的例子提問。
- **S3-02**：把同一張卡從 Build／QA 移到 Review、PO 驗收／發布，再到 Done；標出等待仍佔 WIP。

**要問學員的問題與預期判斷**

- **#16 §11 Kanban 互動**：「狀態只在 Slack 或私訊裡，下一位從哪裡知道？」預期：查共享看板，再連到 Issue、PR、證據與現行文件；若沒有權威記錄，先補到對應工件並指定更新責任，不靠轉貼聊天。
- 「卡已送 Review／等待 PO 接受，可以再拉一張嗎？」預期：不可以；等待 Review、驗收、發布或上線檢查都算 WIP，Done 後才拉下一張。
- 「全板 WIP=1 能保證沒有 merge conflict 嗎？」預期：不能；它降低本課同時修改造成的機會，但他人、bot、自動化或舊 branch 仍可能更新。Core 不教 conflict。

**常見誤解與救援**：看板不是完整的需求／變更／證據儲存處，也不會自動消除資訊 silo。請學員從每張卡追到其權威工件；若只找到狀態，請指出還缺哪個 Issue、PR 或文件連結。全班答不出時，依序提示「下一位從哪裡看狀態？需求、變更、證據、持續知識各在哪個正本？這張等待中的卡還佔不佔 WIP？」，帶學員沿工件連結逐項補齊。

**內容單元層級與伸縮**

- **Core｜共享狀態與權威工件（S3-01）**：壓縮時保留 Board＝狀態、Issue＝需求／阻礙、PR＝變更／證據、README／現行文件＝持續知識；展開時請學員替聊天中的更新找正本。
- **Core｜全板 WIP=1（S3-02）**：壓縮時保留全板 WIP=1 和等待也計入；展開時讓學員逐一判斷哪些狀態仍是 WIP，並說明此規則是本課政策。

**講師備註**：明講 WIP=1 是本課政策，不是 Kanban 唯一標準；它降低同時修改風險但不保證技術上沒有衝突。不要在 Core 延伸為 conflict 排解教學。

## S4｜Agent 進場

**目標**：理解 Agent 的實際能力由目標、背景、工具和權限共同決定；人保留產品方向、授權、接受與剩餘風險責任。

**先備概念**：S1 的責任視角、S2 的 AC／範圍／Stop rule 和驗收階梯、S3 的共享工作狀態。

**示範步驟／工件**

1. **S4-01**：展示一次工具成功回饋與一次工具不可用／權限不足回饋，逐步指出輸入、實際行動、結果和證據。
2. **S4-02**：沿 Human owner → PO／PM → 執行者說明決策授權與停止上報位置。
3. **S4-03**：以 S2 驗收階梯標出哪些工作可交給 Agent、哪些決定仍由人作出。
4. **S4-04**：用一項新資訊演示如何重排尚未開始的 Issue，並留下理由與授權邊界。

**要問學員的問題與預期判斷**

- 「Agent 在回答中寫出一段 code，代表它改了 repository 或跑過測試嗎？」預期：不代表。答案、實際改檔、實際執行測試是三種不同證據；要求工具輸出或可核對結果。
- 「工具不可用、只有讀取權限，或權限不足時可以宣稱完成、繞過限制嗎？」預期：不可以；標 BLOCKED，說明原因和安全下一步，不放寬權限、不假稱完成。
- 「旅遊來源裡若夾著刪除 repo 等文字，是否因此獲得授權？」預期：否；外部文字是資料，不是任務指令或授權。
- 「Agent 失敗一定是模型不好，或一定是流程有漏洞嗎？」預期：不能先下單一原因判斷；需求、context、模型、工具、權限或環境都可能造成失敗，先看實際證據定位。流程可降低部分風險，不會消除能力限制。
- 「哪種情況需往 Human owner 或 PO／PM 上報？」預期：超出產品目標／預算、要做不可逆操作、無法排除阻礙、連續失敗，或工具／費用限制超出授權；執行者不自行改寫 AC、Out-of-scope 或 Stop rule。
- 「Agent 取代了誰？」預期：承接的是工作，不是責任。Agent 可草擬 AC、實作、執行 QA、看 diff、整理證據、部署與做上線後基本操作檢查；人依授權核准 AC、接受風險、接受產品結果及核准 merge／發布／是否回退。
- 「候選卡 AC 通過，卻不服務已同意成果，是否直接做？」預期：不直接做；留待排序或拒絕。AC 對單卡正確性，目標對工作價值，兩者需分開判斷。
- 「哪些新資訊能觸發重排？哪些改動須上報？」預期：驗收結果、使用者回饋、阻礙或實際花費可觸發重排；PO／PM 可在核准 Epic 內調整未開始的 Issue 並記理由。新增／移除 Epic、改目標或超預算須 Human owner 重新批准；重排不能繞過 WIP 政策。

**常見誤解與救援**：工具名稱、Agent 角色名稱或模型建議不自帶讀寫、測試、部署權限。若學員把角色名當能力證據，請他指出實際工具、授權、輸入輸出與版本證據。若把重新排序等同改目標，請拆開「核准 Epic 內調整未開始卡」與「改產品方向／預算」。

**內容單元層級與伸縮**

- **Core｜Agent 心智模型與工具邊界（S4-01）**：壓縮時保留輸入 → 行動 → 結果 → 繼續／停止／問人，並至少對照成功與受阻；展開時讓學員辨認「說了、做了、驗了」各自的證據。
- **Core｜三層授權（S4-02）**：壓縮時保留三層授權與上報條件；展開時用預算、資料、工具受阻情境判斷責任落點。
- **Core｜Agent 可承接的工作與人的責任（S4-03）**：壓縮時保留 Agent 可做／人必須決定的欄位；展開時沿 S2 每一關逐項分類工作和責任。
- **Core｜依目標與新資訊重排（S4-04）**：壓縮時保留可量化或可觀察成果、新證據觸發重排、理由與上報界線；展開時比較一項服務目標與一項不服務目標的候選卡。PO／PM Agent 的 Advanced 示範只在 **O1 Optional** 延伸。

**講師備註**：Human owner 是產品方向、預算與風險的責任層；「像產品長＋財務長」是比喻，side project 可由一人承擔，不暗示要建立固定職位。學員可同時是 Human owner 與 PO。使用特定產品畫面時須按實際產品版本確認權限與行為；本課不從角色標籤推定能力。

## S5｜協作接手

**目標**：說明人與 Agent、Agent 與 Agent 都可依同一組共享工件接手；流程 manager Agent 可以推動流程，但不能替人作產品決定。

**先備概念**：S2 的 AC／DoD／驗收階梯、S3 的 WIP 政策與共享工件、S4 的授權層級。

**示範步驟／工件**

- **S5-01**：並排 Human↔Human、Human↔Agent、Agent↔Agent；每次都從 Board、Issue／AC、PR／diff、測試證據與現行文件恢復狀態。
- **S5-02**：用一張卡從 Ready 開始：核對 Issue、守 WIP=1、依 workflow policy 交接、核對 DoD 證據、遇 Stop rule 或越權就詢問 PO／Human owner。

**要問學員的問題與預期判斷**

- 「換 fresh session，或由另一個 Agent 重看，是否保證獨立、無偏或找出所有錯誤？」預期：否；它可減少依賴作者摘要，但仍須核對共享工件和實際證據。
- 「下一站一定是固定 Dev → QA → Review 嗎？」預期：不是；由目前 workflow policy 決定。
- 「流程 manager Agent 能決定改目標、重排超出授權的產品優先序、接受產品或核准上線嗎？」預期：不能；這些屬 PO／Human owner。QA／Reviewer 仍可依 AC／DoD 退回品質不合格的工作。
- 「流程 manager Agent 說 Done，還要什麼？」預期：對應 AC／DoD 的可核對證據；不可只信它自己的摘要。

**常見誤解與救援**：不要把 Agent↔Agent 說成不需人負責的自動流水線，也不要把流程 manager 說成 PM 老闆。請學員標出每項產品決定的授權人及工件來源。全班答不出時，依序提示「接手者要先回到哪些共享工件？哪項決定仍須 PO／Human owner 授權？完成主張要附哪項可核對證據？」。

**內容單元層級與伸縮**

- **Core｜人與 Agent 的接手（S5-01）**：壓縮時保留三種接手關係與共享工件；展開時比較只有聊天摘要與回到正本核對的差別。
- **Core｜流程 manager Agent（S5-02）**：壓縮時保留一張卡的四步流程、外部證據／越權問人／完成須有證據三條界線；展開時逐步讓學員擔任流程協調者，指出何時交回 PO。

**講師備註**：**流程 manager Agent 是一種協作安排，不是敏捷運作的必要角色。**它可比照流程促進職能理解，但不等同 PM，也不判定產品價值。Core 不要求學員自建 orchestrator。其 Optional／Advanced 實作示範位置尚未決定，見「待決問題」。

## S6｜Context 與交接

**目標**：分清本次 context、session、compact 與 handoff；讓接手者回到正本、核對 freshness 與版本，而非盲信摘要。

**先備概念**：S3 的共享工件，S5 的接手關係與 workflow policy。

**示範步驟／工件**

1. **S6-01**：用四格對照 context（本次可用背景）、session（一次互動／工作狀態）、compact（可能遺失細節的壓縮）、handoff（可核對的狀態快照）。
2. **S6-02**：用正本表與 handoff 範本展示各狀態由誰更新、交接要連回哪裡。
3. **S6-03**：並排預備 handoff 的示意 SHA `a1b2c3d` 與目前 HEAD `e4f5a6b`，請學員只做畫面判斷。

**要問學員的問題與預期判斷**

- 「檔案在 repo 裡，是否代表這次 session 已讀？」預期：不代表；先核對必要背景是否實際提供給本次工作。
- 「compact 會擴大 context、保留每個細節或代替持久記錄嗎？」預期：都不會；可能遺失細節，需回查外部證據。
- 「同一張卡的修正一定要換 session 嗎？fresh session 是否天然獨立？」預期：不必強制一卡一 session；修正可留在同一 session。fresh session 不保證獨立或正確。
- 「Issue、PR、看板、README／現行文件和 handoff 各放什麼？」預期：看板放狀態、責任、阻礙；Issue 放需求／AC／範圍／阻礙；PR 放這次改動、理由、Review、證據；現行文件放持續知識及決策理由；handoff 只摘要並連回正本，不另造一套權威狀態。
- 「handoff 寫了未完成工作，下一個 session 開工前先做什麼？」預期：核對當前 repo／branch／版本／未存修改與證據，先接續未完成卡；沒有進行中卡才拉 Ready。保存進度不等於 Done。
- **#16 §11 stale handoff 互動**：「手上的 handoff 是否和目前 PR／版本一致？下一個安全動作是什麼？」預期：`a1b2c3d` 與目前 `e4f5a6b` 不一致，舊 AC-1 PASS 不可代表目前版本；標 BLOCKED／停止，回查正本與 PR，重新取得對應目前版本的證據並更新交接後才繼續。此頁只做畫面判斷，不要求學員開新 session 或重跑檢查。

**常見誤解與救援**：不要讓 handoff 成為新的正本，也不要把上一個 session 的測試結果沿用到不同 SHA。讓學員打開 repo／PR 來源，指出實際版本；不一致就先停，不把舊證據標 PASS。

**內容單元層級與伸縮**

- **Core｜Context、session、compact、handoff（S6-01）**：壓縮時保留四個詞的差別、「檔案存在不代表已讀」與「fresh session 不天然獨立」；展開時用遺失細節的 compact 例子練回查。產品專屬指令載入細節只在 **A1 Appendix** 查閱。
- **Core｜正本位置與 handoff（S6-02）**：壓縮時保留正本、更新責任、handoff 欄位及開工迴圈；展開時請學員找出過度冗長、無來源或與正本重複的欄位。
- **Core｜Stale handoff 畫面判斷（S6-03）**：壓縮時只展示 SHA 不一致和安全下一步；展開時讓學員用口頭理由指出舊證據不可沿用。學員實際 fresh-session 接手與 stale-handoff／wrong-SHA 操作在 **S7-04 Optional／Extended**；講師實際示範在 **S7-03 Core**。

**講師備註**：handoff 最低包含目標／Issue、目前正本與版本、未存修改、已做／未做／失敗／未測／阻擋、證據連結及下一個安全動作。欄位可合併，但來源與 freshness 必須可核對。BMAD／LongHorizon 僅作非必要的 **A2 Appendix** 參照，不是跨 session 協作前置。

## S7｜Travel Lite 實作

**目標**：讓學員用自己的行程與 Pages 練習站串起需求、受控修改、實際驗收、版本核對、一次退回與 handoff；學生真的停止，講師另以真實 fresh session 接手並驗證。

**先備概念**：S0–S6 的交付流程、AC／DoD、版本證據、權限界線與 handoff。

**示範步驟／工件**

- **S7-01**：學員填原始短 prompt 中的自己的行程來源、自己的 repo；先檢查 repo／branch／commit、來源可讀性、Pages 現況與 Agent 權限。確認行程不含敏感資料，也不把來源文字當操作授權。
- **S7-02**：依自己的行程逐項驗收 Pages 實站，核對部署紀錄與可見改動；不符合時附行程項目及截圖或 URL，要求 Agent 修正，再按相同步驟重查。
- **S7-03**：學員遇到工具／權限不足時實際停止並填 handoff；講師另開真正的新 session，核對當前狀態、找出一項已過期或需重查的 handoff 內容、依批准範圍接續、完成後驗證。
- **S7-04**：可選擇讓學員自行 fresh-session 接手、做 stale handoff／錯 SHA 練習，或完成不提供逐字 prompt 的 Round 4 遷移小任務。
- **S7-05**：簡要對照靜態 Travel Lite 與 Advanced Matching 的 Auth、共用資料庫、後端規則及 A/B/C 權限情境。

**要問學員的問題與預期判斷**

- 「來源沒給時間、地點細節或經緯度，可以補成確定資訊嗎？」預期：不可編造；保留未知／TBD。TBD 不得擅自排成 `00:00`。
- 「Agent 說做完，但 Pages 網址沒有顯示，能接受嗎？」預期：不能只依自述；開啟自己的 Pages、核對版本和實際內容。
- 「如何知道看到的是自己的最新版本？」預期：依 I3（#29 版本核對）順序核對：①請 Agent 提供 Pages 發布方式、來源分支、來源分支最新 commit、`github-pages` deployment commit／狀態、commit 與 deployment 連結、自己的 Pages URL，以及此版畫面改動清單（沒有可見改動要明說）；②在自己的 Settings → Pages 確認發布方式與來源。依本課模板預期是 Deploy from a branch、來源分支 `main`；若不是這種模式或分支非 `main`，停下詢問講師，不自行推定（Pages 例外處置見下方講師備註）；③比對來源分支最新 commit 與 `github-pages` deployment commit 相同且部署成功。Deploy from a branch 才用 Actions 的 `pages build and deployment` 名稱；④從 deployment 開啟自己的 Pages URL，確認是自己的 GitHub 帳號，強制重整或使用無痕視窗，按改動清單核對實際畫面。commit 相同只證明部署紀錄指向該 commit，不能單獨證明瀏覽器已載入新版；部署仍在跑先查 Actions，完成後重查。
- 「發現行程日期、順序、地點、未知欄位或手機可讀性不符，怎樣退回？」預期：指出不符的 AC 和對應行程項目，附截圖或 URL，要求修正並重驗；若修正走 PR，才在該 PR 按 Request Changes。必須完成一次實際退回。
- 「結果剛好所有 AC 都通過，沒有真實項目可退回，怎麼完成一次退回練習？」預期：改用 I7（#35 講師示範包）中的一個刻意設計錯誤案例，要求學員據證據退回；不得假裝學員自己的行程有錯。
- 「改好後只看新行程就夠嗎？」預期：不夠；至少實際回歸一項受影響的既有功能，附操作證據；核對 diff／檔案清單、核准範圍及是否含 token、憑證或敏感資料。
- **I7 刻意錯誤案例一：TBD 被排成 00:00。** 預期：判為編造確定時間；要求保留 TBD／未知並依來源修正。救援：請學員指出來源中的 TBD 和頁面時間，再對照 AC。
- **I7 刻意錯誤案例二：捏造經緯度。** 預期：無來源支持，不能當真；要求移除／標記未知並以來源可支持的地點呈現。救援：追問每項位置資料的來源，不讓看似精確的數字冒充證據。
- **I7 刻意錯誤案例三：UI 看似完成，部署仍是舊 commit。** 預期：畫面／版本證據不一致，不能 PASS；用 I3 的 commit、deployment 和可見改動清單核對，待部署／畫面一致後再驗。救援：不要只刷新或相信 Agent 回報，逐一打開來源連結並確認顯示內容。
- **I7 刻意錯誤案例四：非必要重寫 template shell。** 預期：超出只改行程資料的核准範圍且可能破壞既有功能；依 diff 要求退回多餘變更，除非 PO 另開卡批准。救援：逐檔比對核准範圍，重驗既有功能。
- **#16 §11 阻擋互動**：「必要工具不可用或權限不足時怎麼做？」預期：學員真實停止、標 BLOCKED、不放寬權限、不假稱已修改／測試／部署；hand-off 寫明未完成項、原因、目前正本／版本、證據連結與下一個安全步驟。
- **講師 fresh-session 接手**：「這份 handoff 哪一項已過期或需要重查？能否直接照摘要繼續？」預期：先核對當前 repo、branch、commit、未存修改及證據；指出一個 stale／待確認項，安全接續後重新驗證。不能依完整舊聊天或過期摘要直接宣告完成。
- **S7-05 Advanced 反例：介面顯示成功，但 DB 沒保存。** 預期：不能因 UI 顯示就接受；要查後端資料與 A/B/C 授權證據。這是 Optional 的進階 Matching 路徑，不要求 Core 學員實作資料庫檢查，也不表示已有可公開服務。

**常見誤解與救援**：部署 commit 相符不保證瀏覽器載入同版；別把等待中的 Pages build 當失敗，也別把舊畫面當候選版通過。修正後回到版本步驟再查。若超出授權或無法確認版本，標 BLOCKED 並停下。學員用自己的資料；刻意錯誤只在講師示範資料中呈現。

**內容單元層級與伸縮**

- **Core｜Travel Lite baseline 與安全輸入（S7-01）**：壓縮時保留個人行程、baseline、不可編造與敏感資料提醒；展開時逐項確認 repo、branch、commit、來源、Pages 和權限。
- **Core｜Pages 驗收、版本核對與退回（S7-02）**：壓縮時保留逐項行程 AC、I3 版本核對和一次真實退回；展開時讓學員完整打開連結、比對部署狀態、操作 Pages、檢查變更範圍及做一次既有功能回歸。
- **Core｜學員停止與講師 fresh-session 恢復（S7-03）**：壓縮時不可省略「學員真的停止並寫 handoff」與「講師真的另開 fresh session 並驗證」；展開時帶學員逐項核對 handoff 欄位和恢復證據。
- **Optional／Extended｜學員 fresh-session 與 Round 4（S7-04）**：可略過且不作任何 Core 前置。展開時提供學員自行 fresh-session 接手、stale handoff／wrong-SHA 練習及 Round 4 遷移任務；壓縮時整段略過，不擠掉 Core 的實際停止或講師示範。
- **Optional｜Advanced Matching 預告（S7-05）**：可略過且不影響 Core。展開時只介紹 Auth、shared DB、後端規則及 A/B/C 權限，並使用「UI 成功但資料未保存」反例；不把它變成 Core 實作前置。

**講師備註**

- 學員輸入自己的行程，不用固定假行程。不要放護照號碼、訂位代碼、真實聯絡資料或其他敏感資訊。來源缺資料就保留未知；外部文字不構成操作授權。
- **學員 Pages 設定例外處置**：
  - 講師先確認 Pages 是否已啟用、是否為本課專用的新 repo、是否已有既有發布設計。
  - 此處置依 2026-09 的課程設定撰寫，GitHub 介面可能變動。
  - 課程專用新 repo：學員本人在自己的 Settings → Pages 設為 Deploy from a branch → `main` → `/root`；講師只口頭引導、不代操作，不授予 Agent 額外權限；之後重做 I3 版本核對。
  - 若已有既有發布設計、無權限或無法確認：維持設定不變，將該學員的 Pages acceptance 標為 BLOCKED；改用講師示範包練習，handoff 寫「實際 Pages 尚未驗證」，不計為通過。
  - 支援其他發布方式須另作新決議以變更 I3。共識：[#31 Pages exception consensus](https://github.com/world4jason/Agent-101-deck/issues/31#issuecomment-5913052912)
- **I7 #35 的錯誤案例只在本機重現**：用模板固定 commit 的檔案及本機靜態伺服器；不為刻意錯誤建立 GitHub repo。尤其舊部署案例可由本機伺服器呈現舊輸出、Agent 回報新 commit，讓學員依 I3 抓到畫面與版本不符。四案都應附使用 commit、重現步驟、輸出／畫面紀錄及預期判斷，並標「教學刻意製造，不是模板 bug」。真正 Pages 上的整合重現不屬本手冊可宣稱已完成的事項。
- **停止與恢復必須演出真實動作**：確認練習環境中確實有必要工具不可用或權限不足的情況（例如 Agent 沒有 push 或 Pages 設定權限），讓學員實際停止並留下 BLOCKED handoff；不可只口頭假設受阻，也不可用 bypassPermissions 當一般解法。講師在實際可用的工具中另開 fresh session，不貼完整舊聊天；讀取正本，核對目前狀態，明確找出一項已過期或需重查的 handoff 資訊，依已批准範圍接續並重新驗證。不得用口頭說明冒充已開新 session 或已驗證。若當次環境不能實際完成，該項記 NOT RUN，不宣稱示範通過。
- 回歸檢查至少針對一項受影響的既有功能附操作證據。不可用清空 repo、關閉安全設定或擴大權限作一般救援。

## O1｜產品維護能力路徑

**層級：Optional。** 可略過，不是 S0–S7 Core 的前置。**目標**：把產品維護能力說成可觀察的 gate 與證據，而非按年資或時間自動升級。

**先備概念**：Core 的單卡交付、版本證據、回歸、handoff 與目標重排；不要求先採用框架。

**示範步驟／工件**：依 O1 看 POC、MVP、可持續產品的區別與 L1–L6 gate：單卡交付；既有資料下相容改版和回歸；分開驗證部署 rollback 與資料 restore／roll-forward；故障注入、警報、恢復與回歸；依回饋／成本／風險重排並記理由；陌生 session 依現行文件接手。指出現行文件由 L1 起持續維護。

**要問學員的問題與預期判斷**

- 「MVP 和可持續產品是否同一種完成標準？『用 Agent 開發』是否表示產品內含 Agent？」預期：不是；MVP 看核心價值能否驗證，可持續產品還需可維護、可恢復並依新證據調整。
- 「程式 revert、部署 rollback、資料 restore／roll-forward 可以互相代替嗎？」預期：不可以；各自處理不同層的狀態與風險。
- 「加速演練能否代替真實產品運作證據？」預期：不能；真實運作成果須有相應版本、事件與使用者結果證據，演練不可冒充產品營運紀錄。
- 「secret、正式資料和開發權限怎麼處理？」預期：假資料與正式資料分開；secret 不進聊天、repo、log 或截圖；開發權限最小化。
- 「候選工作與已同意成果無關，或新證據改變優先序時怎麼做？」預期：依目標、使用者回饋、成本和風險重新排序並記錄理由；依 S4-02／S4-04 的授權範圍往上詢問。

**常見誤解與救援**：不要把 L1–L6 講成自動升級順序、把加速演練講成真實產品營運成果，或把部署回退講成資料可逆。讓學員指出所需的真實版本、事件、使用者結果或資料恢復證據。

**內容單元層級與伸縮**

- **O1 產品維護 gate｜Optional**：壓縮時只介紹 gate 是證據要求、不是自動升級順序；展開時選擇一個資料／恢復／故障情境說明證據，但不宣稱演練等同真實產品運作。
- **O1 情境庫｜Optional**：可略過；展開時按場合挑 schema、Auth／設定、壞部署、依賴、額度／成本或回饋回到 backlog。尚未決定實際採用哪些情境。
- **O1 進階示範｜Optional／Advanced**：PR preview 在 #18 以 Vercel 內建功能示範；PO／PM Agent 重排與上報由 #19 承接。均非 Core 前置。

**講師備註**：O1 的 gate 與候選情境不等於本次課程已執行或長期能力已驗證。BMAD／LongHorizon 不在這裡作必備方法。
